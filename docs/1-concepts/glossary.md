# Glossary

Every document in this repository uses the terms below with exactly these meanings. When a document needs one of these concepts it uses the term as written here and links back to this page instead of re-defining it.

## Nodes and Processes

| Term                              | Definition                                                                                                                                                                                                                       |
| :-------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Server**                        | The P2P server process (`node src/server/main.ts` or the Docker image). One TCP listener (default `:4444`) carries signaling, presence, shared state and the socket relay for its one room. See [Server](../2-server/server.md). |
| **Client**                        | An instance of `P2PClient`, the client driver. Holds one control socket to the Server and zero or more links to other peers. See [Client API](../4-client/client-api.md).                                                        |
| **FullStacked runtime** (runtime) | The environment that runs FullStacked application code. It provides `node:net`, `node:events` and the other Node.js shims the Client needs.                                                                                      |
| **FullStacked CLI**               | The runtime running under Node.js (`fullstacked -f script.ts`, the `platform/node` binding). It has no WebRTC API, so every Client in it is socket-only.                                                                         |
| **FullStacked webview**           | The runtime running in a browser engine (desktop and mobile apps, and the headless Chromium used by the integration tests). It has the WebRTC and media APIs, so its Clients use links and media.                                |

## Room and Peers

| Term                  | Definition                                                                                                                                                                                                                                                                                                                    |
| :-------------------- | :---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Room**              | Everyone connected to one Server. A Server has exactly one room: every authenticated peer session is in it, and presence, messages and shared state are shared by all of them. Separate rooms are separate Servers.                                                                                                           |
| **Session**           | One authenticated control socket. Identified by a server-generated `sessionId` (random, 22 base64url characters). A reconnecting Client gets a new session.                                                                                                                                                                   |
| **Peer**              | A visible session: one device of one user, as listed by `getActivePeers()`. Inspector sessions are sessions but not peers. Presence, links, transports and `meta` are per peer.                                                                                                                                               |
| **`peerId`**          | The application-level identity of the user behind a peer (`peer.id` in `auth`, e.g. `usr_alice`). **Not unique**: the same user signed in on a laptop, a phone and a CI job is three peers sharing one `peerId`. Defaults to the `sessionId` when omitted. See [Identity](architecture.md#2-identity-users-devices-sessions). |
| **`deviceId`**        | Identifies the device (more exactly, the `P2PClient` instance) behind a session, chosen by the Client (`deviceId` in `auth`; random per `P2PClient` by default, kept across its reconnects). A new session with the same `peerId` **and** `deviceId` replaces the older one (`session_replaced`).                             |
| **Target**            | Who a direct message or request is for: a `peerId` (every peer of that user, i.e. all their devices) or a `{ sessionId }` (exactly one device).                                                                                                                                                                               |
| **`PeerInfo`**        | The public description of a peer: `{ peerId, sessionId, deviceId, name, meta, role, capabilities, connectedAt }`. See [Protocol Spec](protocol-spec.md#41-peerinfo).                                                                                                                                                          |
| **Role**              | `admin`, `rw` or `ro`, resolved from the credentials. See [Auth & Roles](../3-subsystems/auth.md).                                                                                                                                                                                                                            |
| **Spectator**         | A peer with role `ro`. Receives everything, publishes nothing.                                                                                                                                                                                                                                                                |
| **Inspector session** | A session opened with `mode: "inspect"`, with any role. Invisible (no presence, no links), receives no relayed traffic, and only runs `schema` and `query` within its role. Used by tools and data explorers. See [Inspection](../3-subsystems/inspection.md).                                                                |
| **Capabilities**      | What a Client's environment supports, sent in `auth`: `{ webrtc: boolean, media: boolean }`. The Server and other peers never offer a link or media chunks to a peer that lacks the capability.                                                                                                                               |

## Transports

| Term                       | Definition                                                                                                                                                                                                           |
| :------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Control socket**         | The Client's single `node:net` TCP connection to the Server (`TCP_NODELAY`). Opened first, kept for the whole session, and the only connection a socket-only Client ever has.                                        |
| **Link**                   | A direct WebRTC connection between two peers: one `RTCPeerConnection` with the `p2p-reliable` and `p2p-ephemeral` DataChannels, plus media tracks when shared. See [Transports](../4-client/transports.md).          |
| **Transport**              | How a frame reaches one given peer: `"webrtc"` (over the link) or `"socket"` (relayed by the Server over control sockets). Chosen per target peer, per frame.                                                        |
| **Socket relay**           | The Server forwarding a frame from one control socket to others. Always available; used for every peer without an open link.                                                                                         |
| **Socket-only**            | A Client whose environment has no `RTCPeerConnection` (Node.js, FullStacked CLI) or that disabled WebRTC (`webrtc: false`). All of its traffic uses the socket relay.                                                |
| **Initiator**              | Of the two peers of a link, the one with the lexicographically greater `sessionId`. It creates the `RTCPeerConnection` offer and is the impolite side of perfect negotiation.                                        |
| **`deliveredTo`**          | The list of `sessionId`s a sender already reached over links, attached to `broadcast`, `state:*` and `media:chunk` frames. The Server relays only to members not in it.                                              |
| **Ephemeral frame**        | A frame sent with `{ ephemeral: true }` (cursors, live strokes) or an intermediate `media:chunk`. Unordered and unreliable on links; dropped by the Server instead of queued when a recipient's socket is backed up. |
| **Backpressure threshold** | 65 536 bytes (64 KiB) of `socket.writableLength` on a recipient's control socket. Above it the Server drops ephemeral frames for that recipient.                                                                     |

## Messages and State

| Term             | Definition                                                                                                                                                                                                                  |
| :--------------- | :-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Frame**        | One protocol unit: a 4-byte `UInt32BE` length followed by that many bytes of UTF-8 JSON. On links the same JSON object is sent as one DataChannel message without the length prefix. See [Codec](../3-subsystems/codec.md). |
| **`reqId`**      | A per-session, client-chosen integer correlating a request frame with its `ack` or `error`.                                                                                                                                 |
| **`msgId`**      | `"<sessionId>:<seq>"`, the unique identifier of a published message. `seq` is a per-session counter starting at 1. Used for deduplication and for matching replies.                                                         |
| **Shared state** | The room's key-value map synchronized to every peer and persisted by the Server. See [State Store](../3-subsystems/state-store.md).                                                                                         |
| **Entry**        | One key of shared state: `{ value, deleted, version, updatedBy, updatedAt }`.                                                                                                                                               |
| **Tombstone**    | An entry with `deleted: true`. Kept so an older write arriving late cannot resurrect a deleted key; purged 24 hours after deletion.                                                                                         |
| **Version**      | `[clock, sessionId]`, the Lamport timestamp of an entry. Versions compare by `clock`, then by `sessionId` (lexicographic). The greater version wins (last-write-wins, LWW).                                                 |
| **Clock**        | A Lamport clock. Each Client and the Server keep one, raises it to the highest clock it has seen, and increments it for every local write.                                                                                  |
| **Snapshot**     | The `state.json` file in `P2P_DATA_DIR`, written atomically (`state.json.tmp` then `rename`).                                                                                                                               |
